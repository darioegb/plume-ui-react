# Upgrading to 1.0

This page lists what changed for someone who comes from the 0.x versions of `plume-ui-react`. From 1.0 on, the
public API follows semver: a breaking change only arrives in a major version, and this page will list it.

## `Checkbox`, `Radio` and `Toggle` are bare controls

They render a single `<input>` and no longer take text as `children`, so there is one `<label>` per control. The
visible text comes from `Field`, with the new `inline` orientation (control first, then the label, with the helper
and error text under it). `className` and `style` go to the `<input>`, and `classNames` and the `CheckboxPart`,
`RadioPart` and `TogglePart` types are gone.

```tsx
// Before
<Checkbox classNames={{ label: 'font-semibold' }}>Accept the terms</Checkbox>

// After
<Field label='Accept the terms' orientation='inline'>
  <Checkbox />
</Field>
```

A control that has no visible text needs an `aria-label`. In a `RadioGroup`, give each option its own `Field`:

```tsx
<RadioGroup aria-label='Plan'>
  <Field label='Free' orientation='inline'>
    <Radio value='free' />
  </Field>
  <Field label='Pro' orientation='inline'>
    <Radio value='pro' />
  </Field>
</RadioGroup>
```

## One name for the value callback and for flags

The value of a component is always reported by `onValueChange`, and a flag is a plain adjective, without `is`. The
components that are a single native `<input>` or `<textarea>` (`Input`, `Textarea`, `Checkbox`, `Toggle`, `Radio`)
keep the `onChange` of the element, with its event.

native ones. The `range` option of `getDateStringByLanguage` has the same change.

## Every element is a part

In 0.x, a component with inner parts styled them through loose props (`inputClassName`, `backdropClassName`...) and
later through a `classNames` record. Both are gone: every element a component renders is a part you can import, with
its own `className`, `style`, `ref` and `data-plume-<component>-<part>` attribute. Given no parts, a component renders
the same default composition as before; when a direct child is one of its parts, it renders your composition, so you
reorder, omit or replace any element like any other React element. The sections below list the parts of each family.

```tsx
// Before
<Input type='password' revealable revealClassName='text-sm' />

// After
<Input type='password'>
  <InputControl>
    <InputField />
    <InputReveal className='text-sm' />
  </InputControl>
</Input>
```

## The look of the `DatePicker` goes on the `DatePicker`

`variant`, `size` and `shape` style the input and the calendar together, so they go on the `DatePicker` and no
longer on the `DatePickerInput`.

```tsx
// Before
<DatePicker onChange={onChange}>
  <DatePickerInput variant='filled' size='sm' />
  <DatePickerCalendar />
</DatePicker>

// After
<DatePicker onValueChange={onChange} variant='filled' size='sm'>
  <DatePickerInput />
  <DatePickerCalendar />
</DatePicker>
```

## `className` goes to the outermost element

`className` and `style` always land on the outermost element a component renders, and the native control is a part
(`InputField`, `TextareaField`, `DatePickerField`...) with its own `className`. It changes for the components that
wrap their `<input>` or `<textarea>`:

## One prop for the texts: `labels`

Every text the library shows or announces is changed with a single `labels` prop, typed per component as
`Partial<<Name>Labels>`. Texts that carry data are functions. The loose props of 0.x are gone.

```tsx
// Before
<Paginator nextLabel='Siguiente' previousLabel='Anterior' getPageLabel={(page) => `Página ${page}`} />

// After
<Paginator labels={{ next: 'Siguiente', previous: 'Anterior', page: (page) => `Página ${page}` }} />
```

## `Select` and the pickers are made of parts

`Select`, `DatePicker` and `TimePicker` no longer take `classNames`. Every element they render is a part you can
import, with its own `className`, `style` and `ref`. Given no `children`, they render the same default composition as
before, and a data-driven part (the chips of a `Select`, the days of a `DatePicker`, the options of a `TimePicker`)
takes a render function to style or replace each item.

```tsx
// Before
<DatePicker onChange={onChange} classNames={{ input: 'font-mono' }} />

// After
<DatePicker onValueChange={onChange}>
  <DatePickerInput>
    <InputControl>
      <DatePickerField className='font-mono' />
      <InputElement position='after'>
        <DatePickerTrigger />
      </InputElement>
    </InputControl>
  </DatePickerInput>
  <DatePickerCalendar />
</DatePicker>
```

With parts, the props that only fill the default (`icon` of a `SidebarItem`, `DropdownItem` and `TreeItemLabel`,
`shortcut` of a `DropdownItem`) have no effect: compose the part instead. The `separatorClassName` of the
`Breadcrumb` context is gone: put the class on `BreadcrumbSeparator`. The attributes `data-plume-sidebar-icon` and
`data-plume-sidebar-label` are now `data-plume-sidebar-item-icon` and `data-plume-sidebar-item-label`.

## Utilities are made of parts

`Collapse`, `ProgressBar`, `Table`, `Carousel`, `Paginator` and `FileUpload` no longer take `classNames`. Every element
they render is a part you can import, with its own `className`, `style` and `ref`. Given no parts, they render the same
default composition as before, and the root switches to your composition when a direct child is one of its parts.

```tsx
// Before
<ProgressBar classNames={{ indicator: 'bg-emerald-500' }} value={40} />

// After
<ProgressBar value={40}>
  <ProgressBarIndicator className='bg-emerald-500' />
</ProgressBar>
```

Three changes move a prop to another element, without an error:

- The `className`, `style` and `id` of a `Table` go to its scrolling container, and the `<table>` is the new `TableElement`. Put the classes you had on the table in `<Table><TableElement className='…'>…</TableElement></Table>`.
- The `className` and `ref` of a `TableEmpty` go to its `<tr>`, and the cell is `TableEmptyCell`.
- With `showValue`, the `className` of a `ProgressBar` goes to the container of the bar and the value. Use `ProgressBarTrack` for the bar.

The data-driven parts take a function: `PaginatorPages` gets each entry (a page or an ellipsis), `FileUploadList` each
file and `FileUploadErrors` each rejection. `showEdges` of the `Paginator` only affects the default composition: when
you compose the list, write `PaginatorFirst` and `PaginatorLast` yourself. The attributes `data-plume-fileupload-file`
and `data-plume-paginator-part="x"` are now `data-plume-fileupload-item` and `data-plume-paginator-x`, and the
attribute of the `<table>` is `data-plume-table-element`. `ProgressBar` is now a client component.

## The `Paginator` counts items, not pages

The `count` prop (the number of pages) is removed. Give the `Paginator` the `total` of items and the `pageSize`, and
it works the pages out (`total / pageSize`). If you only have the number of pages, pass `total={pages * pageSize}`.
The `total` also feeds the new `PaginatorSummary`, and a `Paginator` with no `total` renders nothing.

```tsx
// before
<Paginator count={10} />
// after
<Paginator total={100} pageSize={10} />
```

## `Slider` and `Rating` are made of parts

`Slider` and `Rating` no longer take `classNames`. Every element they render is a part with its own `className`, `style`
and `ref`. Given no parts they render the same default composition as before, and a data-driven part takes a function:
`SliderMarks` gets each mark and a `Rating` gets the position of each star.

```tsx
// Before
<Rating classNames={{ empty: 'text-gray-300', filled: 'text-amber-500' }} variant='unstyled' />

// After
<Rating variant='unstyled'>
  {(position) => (
    <RatingItem position={position}>
      <RatingEmpty className='text-gray-300' />
      <RatingFilled className='text-amber-500' />
      <RatingRadio />
    </RatingItem>
  )}
</Rating>
```

a key of `classNames` are parts you import.

## `Carousel` has three variants

`variant` takes `solid`, `overlay` or `unstyled`: `outline` and `ghost` are gone, and the buttons of a carousel that
still asks for them lose their look. Use `variant='unstyled'` and give the buttons your own classes:

```tsx
// Before
<Carousel variant='outline'>

// After
<Carousel variant='unstyled'>
  <CarouselPrev className='rounded-full border border-gray-300 p-2' />
</Carousel>
```

## `useClickOutside` is removed

The overlays of the library close with their own handling of Escape and of a press outside. If you used the hook for
something else, a `pointerdown` listener does the same:

```tsx
useEffect(() => {
  const close = (event: PointerEvent): void => {
    if (ref.current && !ref.current.contains(event.target as Node)) onClose()
  }
  document.addEventListener('pointerdown', close)
  return () => document.removeEventListener('pointerdown', close)
}, [onClose])
```

## The theme: `zIndices`, `breakpoints` in `rem`, and fewer variables

The z-index scale has names instead of numbers, and the typo is fixed: `theme.zIndeces` is now `theme.zIndices`, with
`sticky`, `overlay`, `modal`, `popover`, `dropdown`, `tooltip` and `toast`. They keep the order the layers had, so a
`Select` still opens over a `Modal`. The variables are `--plume-z-<name>` and the Tailwind utilities `z-<name>`.

`theme.breakpoints` is for your own code (`useTheme().theme.breakpoints`, a `useMediaQuery`). The `Sidebar` and the
`Navbar` fold at the `sm`, `md` and `lg` of the default theme, because their CSS uses `@media` queries, which cannot
read a variable. The build writes those queries from `defaultTheme.breakpoints` (`@media (--md)` in the source), so the
widths of every component come from one place: `sm` 40rem, `md` 48rem, `lg` 64rem, `xl` 80rem and `2xl` 96rem, the
same as Tailwind v4. The calendars of the `DatePicker` now stack below `md` (48rem, before 45rem) and the `Paginator`
tightens its spacing below `sm` (40rem, before 30rem).

## The CSS of Plume is in the layer `plume`

`plume-ui-react/styles.css` now puts all its rules in `@layer plume`, after declaring `@layer base, plume, components,
utilities;`. A `className` or a rule of yours wins over Plume without `variant='unstyled'` and without raising the
specificity, and Tailwind v4 utilities such as `px-5` win too.

The other side is that CSS with no layer also beats Plume. If you use Bootstrap, `normalize.css` or the preflight of
Tailwind v3, import it into a layer that comes before `plume` (`@import '...' layer(reset)`, after
`@layer reset, base, plume, components, utilities;`), or the reset will remove the padding of the buttons and the
borders of the inputs. See **Customizing styles**.

## The default theme is in the stylesheet

`plume-ui-react/styles.css` declares the default tokens (`:root` for light mode and
`[data-plume-color-mode='dark']` for what changes in dark mode), so the components render with their colors, spacing
and shadows even without a `<ThemeProvider>`. The provider is still the way to change the theme and the color mode,
and it now writes inline only the variables that differ from the default, so the HTML it renders on the server is
much smaller (a default theme emits about 40 variables instead of more than 300).

Because the default values no longer come from the provider, a variable that is not in your theme is not on the
element: read it with `getComputedStyle` instead of `element.style`. `plume-ui-react/tokens.css` has only the tokens,
for an app that builds its own components over them.
