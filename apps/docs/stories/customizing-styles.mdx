# Customizing styles

Every component can be restyled, from a light touch to a full replacement. Pick the lightest option that does what you
need.

## `className` in every variant

`className` and `style` of a component go to the outermost element it renders. Every other element is a part you can
import, and each part takes its own `className`, `style` and `ref`:

```tsx
<Input type='password' className='mt-4'>
  <InputControl>
    <InputField className='font-mono' />
    <InputReveal className='opacity-60' />
  </InputControl>
</Input>
```

The class is added **next to** the Plume classes of the part, in the `outline`, `filled`, `solid` and every other
variant. It does not replace them, but it wins: the CSS of Plume is in the cascade layer `plume`, and CSS with no layer
beats CSS in a layer whatever its specificity, so `px-5` or a rule of yours for the same property always overrides the
one of Plume.

## Cascade layers

`plume-ui-react/styles.css` starts with `@layer base, plume, components, utilities;` and puts everything inside
`@layer plume`. The order is the one of the layers that come before, so:

- **Your own CSS and the utilities of Tailwind v3**: no layer, so they win over Plume. Nothing to do.
- **Tailwind v4**: its utilities are in the layer `utilities`, which comes after `plume`, so they win. Declare the
  order first if you import Tailwind before Plume: `@layer theme, base, plume, components, utilities;`.
- **A reset with no layer** (Bootstrap's reboot, `normalize.css`, and the **preflight of Tailwind v3**) **also beats
  Plume**: its `button { padding: 0 }` or `* { border-width: 0 }` would strip the styles of the buttons and the inputs.
  Import it into a layer that comes before `plume`. With Tailwind v3, turn the preflight off (`corePlugins: {
  preflight: false }`) and import a reset of your own the same way:

```css
@layer reset, base, plume, components, utilities;

@import 'bootstrap/dist/css/bootstrap.min.css' layer(reset);
@import 'plume-ui-react/styles.css';
```

Tailwind v4's preflight is already in `base`, which comes before `plume`, so it needs nothing.

Adding what Plume does not set (`mt-4`, `max-w-md`, `ring-2`, `hidden`) always works.

## `variant='unstyled'`

`variant='unstyled'` drops every Plume class and keeps only yours, so you style the component from scratch with
Tailwind or Bootstrap. It applies to the root and to all its parts at once:

```tsx
<Input variant='unstyled' className='rounded-lg border border-gray-200 px-4 py-2.5 focus:ring' />

<Input variant='unstyled' className='form-control form-control-lg' />
```

What `unstyled` keeps is what makes the component work, not how it looks: the flex row that holds a chevron, the layer
that centers a modal, the reset of a `<button>` or a `<dialog>`. Those rules have zero specificity, so any class of
yours overrides them. The calendar of the `DatePicker` also keeps its structural classes (the grid of days), and it is
themed with `colorScheme` and the `--datepicker-*` variables.

Every story of Tailwind and Bootstrap in the components shows the component in `unstyled` with those frameworks.

## Styling states

Parts expose their state as attributes, and every part carries `data-plume-<component>-<part>`, so you can style a
state without a class of your own:

```tsx
<InputField className='data-[invalid]:border-red-500 data-[disabled]:opacity-40' />
```

```css
[data-plume-select-option][aria-selected='true'] {
  font-weight: 600;
}
```

The attributes that exist depend on the part (`data-open`, `data-disabled`, `data-invalid`, `data-active`...) and
the ARIA state of the element (`aria-selected`, `aria-checked`, `aria-expanded`) is always there too.

## Colors and tokens

`colorScheme` takes any key of the theme palette, custom ones included, and the tokens of `ThemeProvider` can be
overridden in light and dark mode. See the **Colors** and **Tokens** pages of the Theme section.
